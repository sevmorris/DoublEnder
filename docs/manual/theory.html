Theory of Operation

This covers the architecture, data flows, and design decisions behind DoublEnder and DoublEnder Cloud, from the audio capture pipeline to the release model.

A double-ender is a standard remote podcast recording technique. The host and guest each record their own microphone locally; a producer combines the two independent stems in post. This eliminates the compression artifacts and latency of a live stream capture and gives the editor full-quality audio from both sides. DoublEnder is the guest's end of that equation.

The design philosophy is deliberately Voice Memos-like in UX simplicity and field-recorder-like in reliability, closer to a hardware recorder (Zoom H6, Sound Devices MixPre) than to a consumer screen recorder: it records continuously to a safe format, mirrors a crash-recovery copy in parallel, and never silently loses a take.

Written for the developer who maintains the codebase. Assumes familiarity with Swift, AVFoundation, and audio fundamentals.

The Three Variants

All three share 100% of the Swift source in DoublEnder/. They differ only in what is compiled in and what assets or credentials are bundled.

Layer Responsibilities

AppDelegate owns three things the WindowGroup lifecycle cannot: borderless window configuration (done before first paint to eliminate chrome flash), the quit intercept (applicationShouldTerminate), and the crash-recovery sidecar scan that must complete before the main window appears.

RecorderViewModel is the single source of truth. It holds AppState, all timers, selectedInputDeviceID, and user preferences. It mediates between AppDelegate's event-driven callbacks and AudioEngine's completion handlers. It is a singleton (shared) because AppDelegate needs access independently of SwiftUI's view hierarchy.

AudioEngine owns all AVFoundation objects. It knows nothing about SwiftUI or app state. It publishes @Published flags and fires callbacks that the VM handles, so the engine can be rebuilt, stopped, or torn down without touching the UI layer.

PCMSidecar is a pure I/O object. It writes a flat raw-PCM crash-recovery file alongside the main output, on the same writer queue as the AVAssetWriter, with no dependency on AudioEngine or the VM.

Design Rationale AVCaptureSession over AVAudioEngine

The pre-1.6 AUHAL-based path had a race condition: AUHAL's kAudioUnitProperty_CurrentDevice setter required the device's hardware stream description to already be committed, but freshly-plugged USB devices sometimes hadn't done so yet, causing silent capture failures or click artifacts regardless of retry delay. AVAudioEngine's installTap requires explicit format negotiation and delivers samples through PCM buffer intermediates.

AVCaptureSession binds the device directly (not via the system default), delivers CMSampleBuffers in the device's native format through AVCaptureAudioDataOutput, and eliminates both the format negotiation and the AUHAL race. The per-buffer PCM conversion that produced click artifacts in every prior attempt is simply not present.

Design Rationale AVAssetWriter over AudioFile / ExtAudioFile

AVAssetWriter streams directly to the output file with no intermediate buffer. It handles AAC encoding internally, manages the moov atom for M4A, and applies any necessary sample-rate conversion (for AAC only; WAV is written at native rate). It is the same foundation Apple uses in QuickTime Player's recording mode and the Camera app, battle-tested at the OS level, with failure surfaces (writer.status, write errors) that are explicit and catchable.

Two Serial Queues

Under the Hood sessionQueue and writerQueue

sessionQueue (.userInitiated): All AVCaptureSession configuration and control runs here. startRunning() is a blocking call; Apple recommends a dedicated serial non-main queue for all beginConfiguration/commitConfiguration/stopRunning calls.

writerQueue (.userInitiated): Set as the setSampleBufferDelegate(_, queue:) argument. Every CMSampleBuffer delivery lands here in serial order — the delegate and AVAssetWriterInput.append run synchronously on this queue. PCMSidecar.append is invoked from the delegate on writerQueue, but the sidecar's disk writes are dispatched to a separate ioQueue so capture is never blocked on sidecar I/O.

stopRecording drains writerQueue with writerQueue.sync {} before taking the writer lock, guaranteeing any in-flight delegate call completes before writer refs are cleared; sidecar.close() / sidecar.discard() then ioQueue.sync to flush pending sidecar writes. writerLock (NSLock) mediates shared state between main-thread callers and the delegate.

No audioSettings on the Output

AVCaptureAudioDataOutput is created with default (nil) audioSettings, so the session delivers CMSampleBuffers in whatever native format the device produces, typically kAudioFormatLinearPCM interleaved at the device's own bit depth and sample rate (e.g. 24-bit at 48 kHz for a Scarlett 2i2, 32-bit float at 96 kHz for some Apollo interfaces).

Every prior attempt to set explicit audioSettings at the capture stage produced click artifacts at format conversion boundaries, at USB device attach/detach and on CoreAudio reconfiguration events. The AVAssetWriter's internal transcoder handles format adaptation far more reliably when it sees the source format hint at writer-input creation time.

The Lazy AVAssetWriterInput

startRecording() creates the AVAssetWriter and stores the output settings (pendingOutputSettings) but does not create an AVAssetWriterInput. That happens in captureOutput(_:didOutput:from:) on the very first CMSampleBuffer.

The reason is sourceFormatHint: the AVAssetWriterInput initializer accepts a CMFormatDescription that describes the source PCM it will receive. With the hint derived from the first buffer's actual format description, the writer knows exactly what to expect and can configure its internal transcoder once rather than on every append. The first buffer's PTS also becomes writer.startSession(atSourceTime:), giving exact CoreMedia timestamps.

Format Resolution: AAC vs. WAV

AAC: kAudioFormatMPEG4AAC, AVSampleRateKey: 48_000, mono, 256 kbps. These are final. The writer downmixes multi-channel input and resamples to 48 kHz internally. Fixed rate is intentional: AAC is a delivery format.

WAV (LPCM): kAudioFormatLinearPCM, 24-bit, little-endian, interleaved, mono. AVSampleRateKey: 48_000 is a placeholder only: kAudioFormatLinearPCM requires an explicit rate or canAddInput returns false, but 48 kHz is never actually used for WAV output.

In the first-buffer delegate path, when the pending format ID is kAudioFormatLinearPCM, the placeholder is replaced with the device's actual sample rate extracted from the buffer's CMFormatDescription before the AVAssetWriterInput is created. A 48 kHz Scarlett gets a 48 kHz WAV; a 96 kHz Apollo gets a 96 kHz WAV. No resampling occurs for WAV.

PCM Sidecar

While AVAssetWriterInput.append streams to the M4A or WAV, PCMSidecar.append(sampleBuffer:) is called from the capture delegate on writerQueue and writes a parallel IEEE Float32 mono stream to a companion file (<filename>.pcmrec). Normalization happens on writerQueue; the actual FileHandle.write runs on a dedicated ioQueue so a slow disk never blocks the writer append. Under light load the sidecar is typically one buffer behind; under disk pressure the gap can grow until onFirstWriteFailure fires — the main recording continues regardless. On stop, sidecar.close() / sidecar.discard() synchronizes ioQueue so all samples dispatched before the delegate returned are flushed before the handle closes.

The sidecar is opened in startRecording() before isRecording is set, using a provisional sample rate from the device's activeFormat. Even a crash before the first buffer arrives leaves a sidecar on disk with a valid header. The provisional rate is patched later via updateSampleRateIfNeeded on every buffer where the rate changed.

DEP2 Header Format

OffsetSizeField
04 bytesMagic: "DEP2" (ASCII)
48 bytesSample rate (Float64, little-endian bit pattern)

164 bytesPayload format code (UInt32, little-endian; 1 = Float32)

DEP1 ("DEP1", 16-byte) omits the format code field. The recovery parser handles both for backward compatibility with sidecars written by pre-1.6 builds. The sidecar flushes to disk via FileHandle.synchronize() every 512 KB of payload; at 48 kHz Float32 mono (192 KB/min) that's approximately every 2.6 minutes.

PCM Normalization: Four Formats

PCMSidecar.normalizedMonoFloatSamples(from:) reads the buffer's AudioStreamBasicDescription and dispatches to one of four helpers. The same function drives the level meter, so the UI always reflects the same averaged-mono signal that ends up in the sidecar.

Under the Hood Float32 · Int16 · Int24 · Int32 normalization
  • Float32 (kAudioFormatFlagIsFloat + 32 bits): reinterpret memory as Float. Non-interleaved multi-channel: take channel 0 only. Interleaved multi-channel: average all channels per frame.
  • Int16 (kAudioFormatFlagIsSignedInteger + 16 bits): divide by 32768.0. Same interleaving logic.
  • Int24 (+ 24 bits): 3 bytes per sample, little-endian. Read b0, b1, b2 and sign-extend: raw = (b2 << 16) | (b1 << 8) | b0; if raw & 0x800000 != 0, set high byte to 0xFF. Divide by 8388608.0 (2²³). This path covers Scarlett, Apollo, and similar pro USB interfaces that deliver 24-bit PCM natively.
  • Int32 (+ 32 bits): reinterpret as Int32, divide by Float(Int32.max).

Any other format (unsupported mBitsPerChannel or mFormatFlags) returns nil. The main writer still records normally; the sidecar gets no data for that buffer.

Abnormal Paths

Device disconnect during recording: audioEngine.onDisconnectedDuringRecording fires on the main thread. RecorderViewModel sets suppressIdleInputLossAlert, stores pendingDisconnectReason, and calls stopRecording. finishWriting is attempted; if the writer was healthy, the file is saved. presentDisconnectAlert runs after the completion block, then switchToFallbackInputAfterLoss rebuilds with the built-in mic.

Session interruption (another app takes the mic): The interruption watchdog arms for 5 seconds. sessionInterrupted = true is published and the UI shows "Input interrupted — reconnecting…" without stopping the clock. If the session recovers within 5 seconds, the watchdog is cancelled and the take continues. If not, the watchdog fires handleRecordingCaptureFailure and the take is stopped and saved.

Data-flow stall (driver silently stops delivering): The data-flow watchdog fires after 3 seconds with no successful append. This catches USB hub starvation, driver firmware hangs, and Bluetooth profile transitions that don't generate an AVCaptureSessionWasInterrupted notification.

Sustained backpressure (writer can't keep up): If AVAssetWriterInput.isReadyForMoreMediaData returns false for 3 consecutive buffers (≈30 ms of dropped audio), tearDownWriterLocked is called. If the writer has already received at least one sample, writer refs are left intact for stopRecording to finalize, producing a partial-but-valid file.

Disk full during recording: diskWatchTimer fires every 5 seconds. If DiskSpaceChecker.recordingBlockedReason returns non-nil, stopRecording() is called immediately. Because the writer is still active, finishWriting usually succeeds.

Duplicate stop calls: RecorderViewModel.isFinalizingRecording is set true at the top of stopRecording and cleared when the engine's completion fires. A second call that gets back RecordingError.noActiveRecording while isFinalizingRecording is true is silently swallowed; the recording was already saved by the first call.

Crash/force-quit: applicationWillTerminate never fires. The PCM sidecar is left open on disk. At next launch, the crash-recovery scan finds it and presents the recovery dialog. See Crash Recovery.

Robustness Architecture

DoublEnder records conversations that cannot be re-recorded. The reliability model is closer to a hardware field recorder than a consumer screen recorder: no recording is lost to a recoverable failure, and no failure is silent.

Watchdog 1: Interruption (5 seconds)

What it covers: AVCaptureSessionWasInterrupted, fired when another app takes exclusive control of the audio hardware (FaceTime, Siri, phone call overlay). Most interruptions last a few seconds and the session resumes automatically.

Mechanism: On notification, arm a DispatchWorkItem for 5 seconds. Cancel it if the session recovers, either via captureSessionInterruptionEnded or a successful sample buffer arriving (whichever is first). If 5 seconds pass without recovery, call handleRecordingCaptureFailure.

UI surface: While the watchdog runs, sessionInterrupted = true is published. The VM surfaces "Input interrupted — reconnecting…" as a yellow badge. The clock keeps running.

Watchdog 2: Data-Flow (3 seconds, re-armed per buffer)

What it covers: Sessions where the driver stops delivering buffers without signalling an interruption: USB hub power starvation, driver firmware hangs, Bluetooth profile transitions where the hardware silently switches to SCO mode. AVCaptureSessionWasInterrupted does not fire for these.

Mechanism: On every call to markDataFlowing (called whenever input.append returns true), the existing watchdog is cancelled and a new DispatchWorkItem is created for 3 seconds. If 3 seconds pass without a successful append, the watchdog fires the same failure path as the interruption watchdog.

Watchdog 3: Input-Health Poll (1 second)

What it covers: CoreAudio's device-list listener can lag behind a physical USB unplug by 100–500 ms. AVCaptureDevice.isConnected flips to false much sooner.

Mechanism: inputWatchTimer fires every second. AudioEngine.checkRecordingInputHealth() reads currentInput?.device.isConnected and checks whether the device UID still appears in availableInputDevices. Either failure triggers triggerRecordingInputDisconnect.

Drop Threshold: 3 Consecutive Drops

AVAssetWriterInput.isReadyForMoreMediaData returning false is a backpressure signal: the writer's ring buffer is momentarily full. A single false is normal. Three consecutive false values (≈30 ms at a 48 kHz, 10 ms buffer) means sustained loss: audio is being dropped, the take is already compromised, and failing sooner triggers sidecar recovery before more audio is lost. On the first drop, droppedFrameWarning = true is published and the UI shows "Dropped frames — check disk."

The Disconnect Latch Chain

Under the Hood Three latches preventing duplicate teardowns

When the interruption watchdog, data-flow watchdog, runtime error, and health poll all arrive at roughly the same moment, three latches ensure exactly one teardown path fires and exactly one user-facing stop occurs:

  1. disconnectStopPending (AudioEngine): Set by triggerRecordingInputDisconnect and tearDownWriterLocked. Guards both methods against re-entrancy; once set, neither fires again for the current take.
  2. didDispatchDisconnect (AudioEngine): Set in dispatchDisconnectIfNeeded. Multiple paths arrive at handleRecordingCaptureFailure → dispatchDisconnectIfNeeded; this latch guarantees onDisconnectedDuringRecording fires exactly once per take. Reset in startRecording.
  3. isFinalizingRecording (RecorderViewModel): Set at the top of stopRecording, cleared in the engine completion block. When AudioEngine has already cleared its writer refs (the first caller won), a second stopRecording gets RecordingError.noActiveRecording back. With this flag true, the VM swallows it as a no-op instead of surfacing a spurious "failed to finalize" error.

The PCM Sidecar as Crash Safety Net

The sidecar parallel-writes the entire session as uncompressed Float32 mono PCM. Because it is a flat append-only file with a self-describing header, even an abruptly truncated sidecar (power loss mid-session) re-wraps into a valid WAV at recovery time. There is no moov atom and no container integrity requirement. The invariant: a sidecar file exists on disk if and only if the main recording is unrecoverable.

On a normal successful stop, sidecar.discard() deletes the .pcmrec file. On any failure where finishWriting could not be called, sidecar.close() leaves the file intact for recovery.

Sidecar write failure mid-take: If any FileHandle.write fails, onFirstWriteFailure fires once and sets audioEngine.sidecarFailedDuringRecording = true. The main recording continues; the sidecar is the backup, not the primary. The VM surfaces "Crash backup unavailable."

Quit Protection

applicationShouldTerminate returns .terminateLater when isCurrentlyRecording is true. The alert offers three paths: Stop & Save (calls vm.stopRecording, stays alive until finishWriting completes, then terminates), Quit Without Saving (vm.abortRecording → cancelWriting() + sidecar.discard()), and Cancel (NSApp.reply(toApplicationShouldTerminate: false)).

Disk Space Fail-Closed

At record start: if DiskSpaceChecker.recordingBlockedReason returns non-nil, state goes to .error(reason) and recording does not start. Thresholds: 50 MB for AAC, 200 MB for WAV. If volumeAvailableCapacityForImportantUsage cannot be queried, the function returns a blocking message rather than allowing recording; a recording cannot start on a volume the app cannot measure.

Device Management and Hot-Plug

Device Enumeration

AudioEngine.refreshDevices() calls AVCaptureDevice.DiscoverySession(deviceTypes: [.microphone, .external], mediaType: .audio) and filters the result to remove CADefaultDeviceAggregate-* entries. These are macOS-internal aggregates CoreAudio auto-creates around the current system default for AUHAL compatibility; picking one is a no-op and confusing to the user.

Hardware vs. virtual classification uses CoreAudio kAudioDevicePropertyTransportType. Devices with transport kAudioDeviceTransportTypeAggregate or kAudioDeviceTransportTypeVirtual are classified as .virtual; everything else is .microphone. The hardwareInputDevices() filter exposes only .microphone devices to the picker, so BlackHole, Loopback, and similar routing devices never appear in the UI.

Four Refresh Triggers

  1. CoreAudio listener (kAudioHardwarePropertyDevices, dispatched to main): fires the moment any device is added or removed from the system device list.
  2. NSApplication.didBecomeActiveNotification: devices plugged while DoublEnder was backgrounded are picked up when the app comes front.
  3. NSWorkspace.didWakeNotification: catches devices that reconnected during sleep.
  4. rebuildSession completion (implicit, via engine config changes).

Hot-Plug Offer

On each refreshDevices, new UIDs that are USB devices trigger onNewUSBDeviceDetected — but only while no take is in progress (AudioEngine skips the callback when isRecording; RecorderViewModel.presentUSBSwitchPrompt also bails on isCurrentlyRecording). RecorderViewModel presents an NSAlert app-modal offering to switch. knownInputDeviceUIDs is updated before firing the callback, so any re-entrant refreshDevices call arriving during the modal's runModal() loop sees the new UID as already known and does not stack a duplicate prompt. The first refreshDevices after init seeds knownInputDeviceUIDs silently; launch-time device population is not a "new arrival."

USB First-Seen Map

recordCurrentUSBDevicesFirstSeen() stamps every currently-present USB device with a timestamp in UserDefaults (usbDeviceFirstSeenAt, keyed by UID). Entries are never pruned; UIDs are stable per physical device. At launch, mostRecentlyConnectedUSBDevice() picks the USB device with the most recent timestamp and offers it via presentUSBSwitchPrompt. This captures "the one I just plugged in" intent when multiple USB devices are present.

setDevice Flow

Under the Hood selectedInputDeviceID.didSet → AudioEngine.setDevice
  1. Pre-check: deviceHasInputStreams queries CoreAudio for input stream count. Zero → set selectedDeviceUsable = false and return (no session rebuild). The previously-bound device keeps recording. Returns true on query failure to avoid false rejections.
  2. System default: setSystemDefaultInputDevice is called for cross-app consistency; other apps that honor the system default follow the pick. Note: some virtual devices accept this call with no error but CoreAudio ignores it silently.
  3. Session rebuild: rebuildSession(with: device, intendedDeviceID: id) tears down the current session on sessionQueue and builds a new one bound to the explicit AVCaptureDevice. After startRunning(), the code resolves intendedDeviceID back to an AVCaptureDevice and compares UIDs. If they differ (CoreAudio ignored the system-default set), selectedDeviceUsable = false is published.

Crash Recovery in Detail

The invariant: the sidecar file exists on disk if and only if the main recording was never successfully finalized. The launch-time scan relies on this to decide what to do.

Launch-Time Scan

AppDelegate.runCrashRecoveryIfNeeded runs after configureMainWindow and before the main window is shown:

  1. Read the Desktop directory. FileManager.contentsOfDirectory(at: recordingsDirectory). If this throws, an alert shows error.localizedDescription and the function returns; an inaccessible Desktop is surfaced to the user rather than silently skipped.
  2. Filter for sidecars. pathExtension == "pcmrec".
  3. Discard empty sidecars (hasRecoverableContent checks file size vs. 20-byte header). Their companion main files: if > PCMSidecar.mainFileValidThresholdBytes (8 KB), the main file is a valid finalized recording; keep it and log a warning. If ≤ 8 KB (stub/aborted container), delete both.
  4. Recover non-empty sidecars. The main window is hidden, NSApp.activate(ignoringOtherApps: true) brings DoublEnder forward, and each recoverable sidecar gets a sequential modal presentRecoveryDialog call. After all dialogs complete, mainWindow?.makeKeyAndOrderFront(nil).
Under the Hood The 8 KB threshold

PCMSidecar.mainFileValidThresholdBytes (8 KB) is the single source of truth for this check in launch-time cleanup and RecoveryModel.hasValidMainFile. It is larger than any valid AAC moov atom from a sub-millisecond take, but small enough that a stub container (where finishWriting was never called) falls below it. The smallest valid AAC M4A the writer produces (even a 0.1-second take with a valid moov atom) exceeds 8 KB. A container where cancelWriting() ran typically has fewer than 1 KB.

RecoveryModel Phases and Prompt Options

RecoveryModel drives the recovery dialog through four phases: .prompt → .working → .success(URL) or .failure(String). The expensive PCMSidecar.recoverToWAV conversion runs on DispatchQueue.global(qos: .userInitiated) so the spinner keeps animating.

When hasValidMainFile = false (interrupted recording, the most common case): RECOVER (re-wrap sidecar to WAV, delete both sidecar and partial main file) or DELETE (delete both without recovering).

When hasValidMainFile = true (sidecar orphaned next to a valid main file: the tiny window between finishWriting completing and sidecar.discard() running before a crash): KEEP SAVED (delete sidecar only), RECOVER, or DELETE.

Recovery WAV Format

PCMSidecar.recoverToWAV reads the sidecar header for sample rate and channel count, writes a canonical 44-byte RIFF/WAVE header (WAVE_FORMAT_IEEE_FLOAT, 32-bit), and streams the sidecar payload in 1 MB chunks. Output path: "{stem} (recovered).wav" adjacent to the main output file, de-duplicated with " (recovered 2)", " (recovered 3)", etc.

Cloud Variant: What's Added

The GCS_ENABLED compilation condition gates all Cloud-only code. Uploader.swift, CloudConnectivity.swift, CloudContentView.swift, upload-related RecorderViewModel branches, and the Cloud UpdateChecker path all compile out in Local and unbranded builds.

GCS Authentication: V4 Signed URL, Entirely On-Device

DoublEnder Cloud has no backend server. Authentication uses GCS V4 signed URLs generated entirely on the client from a bundled GCP service-account JSON key:

  1. Load doublender-10af32ff2d11.json from the app bundle (Bundle.main.url(forResource:))
  2. Parse private_key (PEM-encoded PKCS#8 RSA key) and client_email
  3. Build a canonical GCS PUT request string per the V4 signing protocol
  4. SHA-256 hash it with CryptoKit
  5. Sign the hash with RSASSA-PKCS1-v1_5 via SecKeyCreateSignature (Security.framework; CryptoKit has no RSA)
  6. The PKCS#8 outer PrivateKeyInfo wrapper is stripped via a minimal DER walk to extract the bare PKCS#1 RSAPrivateKey that SecKeyCreateWithData expects

The resulting URL is valid for 15 minutes, enough for any take to upload, with no long-lived credential exposed. The URL is single-use.

Upload Flow

stopRecording completion (.success(.some(url))) triggers: state = .uploading → setPendingUpload(path:) persisted to UserDefaults before the PUT starts (survives a mid-upload quit) → performUpload() off the main actor → URLSession.upload(for:fromFile:) PUT to the signed URL → progress via urlSession(_:task:didSendBodyData:...) delegate.

On HTTP 200–299: clearPendingUpload(), state = .ready, UploadConfirmation.present(success: true). On failure: exponential backoff [2s, 4s, 8s] across up to 3 retries, staying in .uploading throughout. After retries exhausted: state = .uploadFailed(fileURL).

The GCS object key is {prefix}/{uuid}/{filename}. The prefix is derived from the bundle ID tail (DoublEnderCloud or DoublEnderCloud-{slug}). The UUID prevents filename collisions when a guest records twice with the same name.

Pending-Upload Recovery

runPendingUploadCheckIfNeeded (in applicationDidFinishLaunching) reads pendingUploadPath from UserDefaults. If the file still exists on disk, PendingUploadPrompt.present shows a modal offering Upload or Skip. If the file is gone (user deleted it between sessions), the path is cleared silently.

CloudConnectivity and the Blue LED

CloudConnectivity (singleton, @MainActor) publishes a single isReady flag: credentialsOK && networkSatisfied. credentialsOK is checked once at init by parsing the service-account JSON. networkSatisfied is tracked live by NWPathMonitor, updating within ~1 second of any path change. The blue LED in CloudContentView reflects connectivity.isReady, solid on/off, not flashing (contrast with the red recording LED, which flashes at 0.75 s).

Update Checker: Cloud vs. Local

Local: queries https://api.github.com/repos/sevmorris/DoublEnder/releases/latest. "Download" opens the GCS permalink (doublender-downloads/DoublEnder.dmg) rather than a version-pinned GitHub asset; the permalink always resolves to the current build.

Cloud: queries the UpdateManifestURL from the bundle's Info.plist. The manifest is a small JSON { "version": "1.7.2cr", "url": "https://…" } written by release-cloud.sh on every release. For branded builds, UpdateManifestURL is set at build time per brand, so each client has its own independent update channel.

App Lifecycle and Release Model

Launch Sequence

applicationWillFinishLaunching: registerBundledFonts (DSEG7 Classic for the seven-segment counter), NotificationService.shared.configure (register "Reveal in Finder" action category), RecorderViewModel.eraseSessionDefaults() (clear custom filename from prior session; runs even after a crash where applicationWillTerminate never fired).

applicationDidFinishLaunching: configureMainWindow (borderless, transparent, object_setClass to KeyableBorderlessWindow), runCrashRecoveryIfNeeded, runPendingUploadCheckIfNeeded (Cloud only), checkForUpdates(silent: true).

Under the Hood Why object_setClass must happen after setStyleMask

SwiftUI's WindowGroup creates a stock NSWindow. After setStyleMask = [.borderless], AppKit's default canBecomeKey returns false for borderless windows; clicks on the window while the app is backgrounded fail to activate it. The fix uses object_setClass to re-class the SwiftUI-owned instance to KeyableBorderlessWindow (overrides canBecomeKey and canBecomeMain to return true).

The class swap must happen after setStyleMask. SwiftUI's NSHostingView.viewWillMove(toWindow:) registers KVO observers keyed on the window class. If the class is swapped before setStyleMask, the subsequent removeObserver:forKeyPath: call fails to find the observer in the class-keyed table and crashes with "Cannot remove an observer … is not registered." After all window mutations are complete, no SwiftUI path triggers another KVO cleanup, so the swap is safe.

XcodeGen Overlay Pattern

The public repo contains project.yml, which builds the Local (DoublEnder) and DoublEnderTests targets. The private Cloud overlay (project.cloud.yml, gitignored) adds DoublEnderCloud and DoublEnderCloudTests targets and pulls in Cloud-only source paths and the service-account JSON.

Before any Cloud build, a Ruby one-liner merges the two YAMLs (base["targets"].merge(cloud["targets"])), writes a temporary .project.merged.yml, and runs xcodegen generate. The merged file is immediately deleted. The .xcodeproj in the repo is always generated from the public project.yml only.

  9. Create DMG: hdiutil create -format UDZO
  10. Notarize: xcrun notarytool submit --wait --keychain-profile WoWoNotary + xcrun stapler staple
  11. Verify DMG: mount, read version, unmount
  12. Tag and push: git tag vX.Y.Zlr, push branch and tag
  13. GitHub release: gh release create with DMG attached; release notes generated from commits since previous tag
  14. GCS permalink: gsutil cp to gs://doublender-downloads/DoublEnder.dmg with Cache-Control: no-cache
  15. Cloud + branded releases: if project.cloud.yml is present, run release-cloud-from-local.sh
  16. Prune old releases: keep the 5 most recent GitHub releases; delete older tags and assets

Constraints and Design Decisions

These are intentional choices that would otherwise look like oversights.

DecisionRationale
No sandbox Sandboxing would require a security-scoped bookmark or a save panel to establish Desktop write access, which adds friction for guests who should just press record. ENABLE_HARDENED_RUNTIME: YES is still set so the binary is notarization-eligible.
No save panel Files go to ~/Desktop/DoublEnder_<timestamp>.<ext> automatically. The DateFormatter uses en_US_POSIX locale (prevents locale-specific AM/PM markers, RTL text, non-Gregorian calendars) at millisecond precision (yyyy-MM-dd_HH-mm-ss-SSS), shrinking the same-timestamp collision window from 1 second to 1 ms.
Mono output Podcast production almost universally uses mono guest stems. Stereo doubles the file size for no benefit; podcast editors sum to mono anyway. Multi-channel input is averaged to mono per frame before encoding.
AAC as default 256 kbps AAC is transparent quality for voice at ~1.9 MB/min. A 1-hour guest recording is ~115 MB, safely below the attachment limit of most email providers. WAV is available for guests explicitly instructed to record lossless, but defaults to off because naive guests will record 90-minute WAVs and struggle to send them.
Meter floor −36 dB The meter answers one question: "Is audio coming in?" The 36 dB range covers what matters: a quiet room with ambient noise sits around −25 to −30 dBFS; speech peaks around −12 to −6 dBFS. The bottom 24 dB (−60 to −36) is below ambient room noise for any practical recording environment. The 1 dB deadzone above dbMin in the meter rendering prevents the leftmost segment from staying lit at idle. This is deliberate: the meter is a signal activity indicator, not a precision level tool.
WAV at device native rate (not fixed 48 kHz) A placeholder 48 kHz is required in pendingOutputSettings or canAddInput returns false, but the actual rate is replaced on the first buffer from the device's CMFormatDescription. A DAW importing a native-rate file needs no sample-rate conversion at the mix stage.
Session defaults cleared at every launch RecorderViewModel.eraseSessionDefaults() runs in applicationWillFinishLaunching, before the VM is initialized. This catches crashes and force-quits where applicationWillTerminate never fired. The custom filename prefix from a previous session cannot bleed into the next launch regardless of how the previous session ended.
Notes metadata not stored in WAV AVMutableMetadataItem with .commonIdentifierDescription is honored by AVAssetWriter for M4A (stored in the moov atom) but silently dropped for WAV. The settings popover shows a warning when WAV is selected.
WRITING indicator: 150 ms trail The "WRITING" label reflects "did AVAssetWriterInput.append return true in the last 150 ms," not "is the capture session running." A session that is running but delivering no data correctly shows a dim WRITING label, a useful diagnostic for stalled-driver scenarios even before the 3-second data-flow watchdog fires.
